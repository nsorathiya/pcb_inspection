# Inspection-Validation Result Persistence

Date: 2026-07-17

## Scope

Schema version 2 adds append/read-only storage for completed paired RGB/height
semantic-validation results. It does not run validation, change inspection
status, create audit events, or expose an HTTP API. Those orchestration and
atomic status/audit decisions remain deferred.

## Migration and backup

Database startup runs explicit numbered migrations in order:

1. `001_initial` creates the original schema version 1 tables.
2. `002_validation_results` adds validation results and findings.

A new database applies both migrations and records version 2. An existing
version 1 database applies only migration 2. Existing inspections, artifacts,
recipes, model versions, and audit events are not rewritten. Startup validates
the authoritative `schema_version` row and required tables, is idempotent at
version 2, and rejects invalid or future versions. The version advances only
inside the migration transaction after the upgrade operation succeeds.

Back up a deployed database before migration. For a live WAL database, use the
SQLite online backup API; alternatively stop the application and copy the main
database, `-wal`, and `-shm` files consistently. Alembic should be adopted when
the project needs branching migrations, downgrade policy, multiple deployed
schema histories, or more complex table/data transformations. It is not a
dependency of this focused migration foundation.

## Tables

`inspection_validations` stores one immutable completed attempt: validation and
inspection identities, contract/policy/validator versions, deterministic
validation key, validation outcome, timestamps, canonical technical/summary
JSON, the complete canonical result, its SHA-256, and creation time.
`(inspection_id, validation_key)` is unique. Outcomes are only
`VALIDATION_PASSED`, `VALIDATION_FAILED`, or `VALIDATION_ERROR`; they are not
PCB classification statuses.

`inspection_validation_findings` stores the result's findings by zero-based
ordinal. `(validation_id, ordinal)` is unique. Severity, category, and optional
artifact type use the authoritative application enums. The typed persistence
boundary also resolves every code through
`contracts/inspection_validation_findings.json`; it has no second code list.
Finding details are canonical JSON objects and path-shaped details are rejected.

Both tables enforce foreign keys. Application repositories expose insertion
and reads only—no update or delete methods.

## Deterministic validation key

`generate_validation_key` hashes UTF-8 canonical JSON with sorted object keys
and compact separators. Its inputs are:

- inspection ID;
- raw RGB and height artifact type, lowercase SHA-256, and byte size;
- optional required technical-evidence artifact identities;
- validation contract version;
- policy ID and version; and
- validator version.

Evidence entries are sorted by type, hash, and size before serialization. The
key excludes paths, timestamps, validation IDs, and request IDs. Identical
technical inputs produce the same lowercase SHA-256; changing a raw hash,
policy version, or validator version changes the key. The key is generated by
the system, not accepted as a client idempotency token.

## Canonical result and hash

`canonical_result_bytes` is the one hash source for a typed
`InspectionValidationResult`. It uses stable field/finding order, sorted JSON
object keys, compact separators, UTF-8, and timezone-aware timestamps normalized
to UTC with `Z`. Persistence first validates the typed result, catalogue order,
summary counts, outcome consistency, timestamp ordering, and safe finding
details. `result_sha256` is calculated from exactly these bytes; database JSON
text handling does not participate in the hash.

## Transaction and replay behavior

The parent result and every ordered finding are inserted in one transaction. A
finding failure rolls the entire attempt back. Persistence does not modify the
inspection, artifact rows, or audit log.

- A new `(inspection_id, validation_key)` inserts the result and findings and
  returns `idempotent_existing=false`.
- A replay with the same key and identical canonical result hash returns the
  existing identity with `idempotent_existing=true`; it adds no findings.
- A replay with the same key but a different result hash raises a typed
  `ValidationPersistenceConflictError` and leaves the stored result unchanged.

## Retrieval

The repository can read by validation ID, read by inspection ID plus key, list
findings in ordinal order, and retrieve an inspection's latest validation. The
latest ordering is `completed_at DESC`, `created_at DESC`, then validation ID
as a deterministic tie-breaker. Typed responses contain no SQLAlchemy internals,
connection details, raw SQL, stack traces, or paths.

## Deferred integration

Standalone persistence continues to store immutable technical evidence without
changing `RECEIVED`, `READY`, `VALIDATION_FAILED`, `ERROR`, or any other status
and without appending audit events. `ValidationCommitService` now reuses the
same validation and canonical persistence logic through an externally owned
transaction when status and audit must be coordinated. See
`docs/inspection_validation_lifecycle.md` for allowed transitions, adoption of
an existing standalone result, concurrency protection, and rollback behavior.

No API or validation-execution wiring exists. Callers that only need immutable
evidence may use standalone persistence; future application/API code that must
affect inspection lifecycle should use the atomic coordinator.
